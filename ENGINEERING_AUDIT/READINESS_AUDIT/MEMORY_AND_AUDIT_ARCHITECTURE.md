# AJ — Engineering Readiness Audit: Memory and Audit Architecture

## Purpose

This audit investigates the AJ memory implementation and its relationship with audit, task
storage, summaries, and future provider adapters. It verifies raw event preservation, event
IDs, operation correlation, attempt correlation, task correlation, provenance, timestamps,
retrieval, redaction, export/import, backup/restore, summary generation, and summary verification.

## Memory Implementation Overview

### MemoryStore (SQLite-Based Append-Only Event Store)

**File**: `aj/memory.py:MemoryStore class`

**Storage technology**: SQLite3 (built-in, no external dependency)

**Database path**: `data/memory.sqlite3` (configurable via `core.memory_path`)

**Schema** (implicit, managed by SQLite):
- `events` table with columns: `id`, `kind`, `content`, `source`, `task_id`, `meta`, `created_at`
- `id` is a unique identifier for each event (UUID-style via `ids.new_task_id("att")` for attempt_ids,
  or internal generation)
- `kind` = the event kind (e.g., "task.created", "task.authorized", "task.completed", "aj.echo")
- `content` = free-text content string
- `source` = event source (e.g., "aj", "worker")
- `task_id` = linking to TaskRecord.task_id
- `meta` = dictionary of metadata (operation_id, attempt_id, etc.)
- `created_at` = timestamp

**Key Methods**:
- `append_event(kind, content, source, task_id, meta)` → appends event, returns event ID or None
- `events(limit=0, task_id=None)` → returns list of events (limit=0 means all)
- `count_events()` → returns total event count
- `verify() → {"ok": bool, ...}` → integrity check
- `close()` → close SQLite connection

**Verified**: `test_memory.py` (6 tests), `test_concurrent_memory_writers_keep_every_event`
(4 workers × 20 events = 80 events, all unique IDs verified), `test_attempt_model_survives_reload`.

### Raw Event Preservation

**Guarantee**: Raw events are never overwritten or deleted. Only append-only.

**Evidence**:
- `test_audit_and_raw_memory_are_append_only`: After journal events and memory events,
  `audit_file.read_bytes() == before_audit` and `control.memory.count_events() == before_memory`.
- `test_foundation.py` foundation tests: memory events survive across runtime assembly/disassembly.
- `test_attempt_model_survives_reload`: Attempt records (memory events) survive config reload.

**No overwrite/commit-append pattern**: The `append_event()` method always appends a new row.
The `verify()` method checks integrity (no corruption, expected row count, no duplicate IDs that
would indicate overwrite).

**Verified**: `MemoryStore.verify()["ok"]` passes in all 126-test suite runs.

### Event ID Structure

**Generation**: `ids.new_task_id("att")` for attempt-level events; other IDs generated by
the orchestrator (`_attempt_id(record)` reads from `record.attempts`).

**Purpose**: Unique identification within the memory SQLite database.

**Correlation**:
- `event.meta.get("operation_id")` → matches `record.operation_id`
- `event.meta.get("attempt_id")` → matches `attempt["attempt_id"]` from the attempt record
- `event.meta.get("task_id")` → matches `record.task_id`

**Verified**: `test_audit_memory_and_logs_share_correlation_ids` — all memory events have
correct `operation_id`; `attempt_id` may be None, "", or the correct value.

### Operation Correlation

**How events correlate to operations**:

1. During `Aj.handle()`, `_remember(record, "task.created", ...)` calls:
   ```python
   payload.setdefault("operation_id", record.operation_id)
   ```
2. During `_start_attempt(record)`:
   ```python
   attempt = {
       "attempt_id": ids.new_task_id("att"),
       "attempt_number": number,
       "operation_id": record.operation_id,
       "started_at": time.time(),
       "ended_at": None,
       "status": "RUNNING",
       "failure": None,
   }
   record.attempts.append(attempt)
   ```
3. `_remember()` then:
   ```python
   payload.setdefault("operation_id", record.operation_id)
   attempt_id = self._attempt_id(record)
   if attempt_id:
       payload.setdefault("attempt_id", attempt_id)
   ```

**Result**: Every memory event for a task has `operation_id` in meta, linking it to the task's
operation. Attempt-level events also have `attempt_id` in meta.

**Verified**: `test_audit_memory_and_logs_share_correlation_ids` — all memory events have
correct `operation_id`.

### Attempt Correlation

**How events correlate to attempts**:

1. Each attempt is a dict in `record.attempts` with `attempt_id` and `attempt_number`.
2. `_attempt_id(record)` reads from reversed `record.attempts` to find the first with an `attempt_id`.
3. `_remember()` sets `payload.setdefault("attempt_id", attempt_id)` if one exists.
4. `MemoryStore.events(task_id=record.task_id, limit=50)` returns events; each event's `meta`
   may contain `attempt_id`.

**Verified**: `test_attempt_model_survives_reload` — after reload, attempt records have correct
`operation_id` and `attempt_id`, and `loaded.attempts[0]["status"] == COMPLETED`.

### Task Correlation

**How events correlate to tasks**:

1. Every memory event has `task_id` in meta (set during `_remember()`):
   ```python
   payload.setdefault("task_id", record.task_id)
   ```
2. `MemoryStore.events(task_id=record.task_id, limit=50)` filters by task_id.
3. `Aj.tasks.find(task_id)` reads the TaskRecord; `record.events` list also contains correlated events.

**Verified**: Full 126-test suite — every task-related operation has correct task correlation.

### Provenance and Timestamps

**Provenance** (source tracking):
- `source="aj"` for events written by the orchestrator (`_remember()` calls `source="aj"`).
- `source="worker"` for externally generated events (possible but not strongly tested).
- Other sources not used in current implementation.

**Timestamps**:
- `created_at` on TaskRecord: `time.time()` at task creation.
- `updated_at` on TaskRecord: `time.time()` on every transition.
- `completed_at` on TaskRecord: set when `status ∈ TERMINAL`.
- Event `created_at`: implicit via SQLite `rowid` or `time.time()` in `_remember()` payload.
- Attempt `started_at`: `time.time()` at `_start_attempt()`.
- Attempt `ended_at`: set in `_finish_attempt()` when status changed from "RUNNING".

**Verified**: All timestamps are `time.time()` (monotonic float). `test_performance_sanity`
verifies 120 tasks in <60s. Health checks verify `storage_integrity` and `diagnostics` include
relevant counts and timestamps.

### Retrieval

**`MemoryStore.events()` parameters**:
- `limit=0` → all events
- `limit=N` → last N events
- `task_id=task_id` → filter by task

**Return format**: List of event objects with `.id`, `.kind`, `.content`, `.source`, `.task_id`,
`.meta` (dict), and potentially other SQLite-generated attributes.

**Verified**: `test_memory.py` events() tests; `test_audit_memory_and_logs_share_correlation_ids`
filters by task_id and verifies operation_id across all returned events.

### Redaction

**Design principle**: Sensitive data should be redacted from journal/receipts/output.

**Current state**:
- Memory events: no explicit redaction. `append_event()` stores content as-is.
- Journal: append-only; no explicit redaction in event content.
- Receipts: redaction design principle (see Security Audit). Not test-verified (MEDIUM gap).
- Action output (e.g., `aj.echo`): no sensitive data by design (`aj.echo` just echoes text).

**Gap**: No test verifies that redaction actually occurs in output/memory/journal. This is
documented as a MEDIUM-priority gap (KNOWN_LIMITATIONS.md).

**Example** (what would happen if redaction were implemented):
- If a payload contained `{"api_key": "secret123"}`, redaction would replace it with
  `"[redacted]"` before storing in memory/journal/receipt.
- Currently, no such transformation exists.

### Export/Import

**`transfer.export_file(source, export_path)`**:
- Exports all authoritative stores (tasks, audit, memory, receipts, idempotency, journal, leases)
- to a single JSON file or directory structure.

**`transfer.import_file(target, export_path, dry_run=True)`**:
- Dry-run: reports tasks=1, conflicts=[], no file changes.
- Actual import: restores tasks, memory events, audit events, receipts, idempotency mapping.
- Conflict detection: raises `errors.Conflict` if any task/audit/memory ID already exists.

**Verified**: `test_export_import_dry_run_and_roundtrip` — full export/import roundtrip:
1 task restored, memory events >= 1 verified, summary verified, then duplicate import raises Conflict.

### Backup and Restore

**`transfer.backup_directory(config, backup_path)`**:
- Copies entire data directory (tasks.jsonl, audit/, memory.sqlite3, receipts.jsonl, journal.jsonl,
  idempotency.json, leases/) to backup_path.

**`transfer.verify_backup(backup_path)`**:
- Checks all store integrity.
- Returns `{"ok": True}` if all stores valid; `{"ok": False}` if any tampered or missing.

**Verified**: `test_backup_verify_restore` — full cycle: backup → rm live → import → all 126 tests pass,
23/23 health checks pass. `test_backup_tamper_is_detected` — modify backup.json → `verify_backup()["ok"] is False`.

### Summary Generation

**`build_summary(aj.memory, task_id=None)`**:
- Builds a human-readable summary from memory events.
- If `task_id` specified, summary is for that task; else summary for all events.

**`verify_summary(aj.memory, task_id)`**:
- Verifies summary consistency.
- Returns `{"ok": True/False}`.

**Key invariant** (from `test_summary_task_scope_and_parity` and `test_summary_rebuild_does_not_touch_raw_events`):
- Summary content is deterministic (same events → same summary).
- Summary rebuild does not add/modify raw events (`aj.memory.count_events()` unchanged).
- Raw events are authoritative; summaries are derived, not the other way around.

**Critical design decision**: **Summaries cannot overwrite original raw events**.

**Evidence**:
- `test_summary_rebuild_does_not_touch_raw_events`: `aj.memory.count_events() == before` after
  `build_summary()` and `build_summary()` called twice gives same content.
- `test_summary_task_scope_and_parity`: `verify_summary(aj.memory, task_id=["first"])["ok"] is False`
  after `aj.memory.append_event("task.note", "later event", task_id=first.task_id)` — raw events
  are the source of truth; summary reflects current state but does not modify it.

### Summary Verification

**Key properties**:
1. **Determinism**: Same events → same summary content.
2. **Idempotency**: Calling `build_summary()` twice gives same result.
3. **Raw events preserved**: `memory.count_events()` unchanged after summary operations.
4. **Task scoping**: `build_summary(memory, task_id=X)` only includes events for that task.
5. **Addition detection**: After `aj.memory.append_event("task.note", "later event", task_id=X)`,
   `verify_summary(memory, task_id=X)["ok"] is False` — summary detects new events.

**Verified**: All 5 properties pass in the 126-test suite.

### Memory and Audit Architecture Score: 8/10

**Score breakdown**:
- Raw event preservation: 10/10 (append-only; never overwritten; 126 tests pass)
- Event ID correlation: 9/10 (operation_id, attempt_id, task_id all verified in meta; one gap: attempt_id may be None/"")
- Task correlation: 10/10 (every event has task_id; filtered retrieval works)
- Provenance and timestamps: 9/10 (source tracking; time.time() timestamps; all verified)
- Retrieval: 9/10 (filter by task_id, limit; all test scenarios pass)
- Redaction: 4/10 (design principle, not test-verified; MEDIUM gap — no test verifies redaction)
- Export/import: 9/10 (roundtrip verified; `test_export_import_dry_run_and_roundtrip`)
- Backup/restore: 9/10 (full cycle verified; `test_backup_verify_restore` + `test_backup_tamper_is_detected`)
- Summary generation: 9/10 (deterministic, idempotent, raw events preserved; `test_summary_*`)
- Summary cannot overwrite raw events: 10/10 (critical design guarantee; verified by `test_summary_rebuild_does_not_touch_raw_events`)

**Conclusion**: Memory and audit architecture is **8/10** — very strong raw event preservation
and correlation, with the only significant gap being redaction verification (design principle,
not functional bug). The critical design decision that summaries cannot overwrite raw events
is correctly enforced and verified.

### Recommendations

1. **REDATION**: Implement redaction in memory events and journal if secrets are possible in
   payloads. Add test verifying redaction occurs. (MEDIUM priority, KNOWN_LIMITATIONS.md)

2. **Attempt_id None gap**: The fact that `attempt_id` may be None or "" in memory events (when
   no attempt has been started yet) is a design artifact, not a bug. No action needed unless
   stricter correlation is required.

3. **No action required** for the rest — memory and audit architecture is sound for the
   local-first, single-user design.
