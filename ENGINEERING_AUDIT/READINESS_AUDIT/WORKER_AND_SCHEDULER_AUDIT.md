# AJ — Engineering Readiness Audit: Worker and Scheduler Audit

## Purpose

This audit inspects the worker lifecycle and scheduler implementation in AJ. It verifies
what worker identity, claiming, heartbeat, graceful shutdown, and task dispatch look like
in the current codebase, and identifies gaps against the project's reliability objectives.

## Worker Lifecycle Overview

### Worker Identity

**Source**: `aj/orchestrator.py:Aj.__init__()` and `aj/lease.py:LeaseManager`

```python
self.worker_id = worker_id or f"{socket.gethostname()}:{os.getpid()}"
```

**Composition**: `hostname:pid` format. Unique per process start. Not persistent across restarts
unless explicitly persisted.

**Verification**: All 126 tests pass with this identity scheme. No two workers share the same
`worker_id` in concurrent test runs (`test_concurrent_task_writers_do_not_corrupt_store`).

### Worker Claim (Execution Lease Acquisition)

**Entry point**: `Aj.handle()` → `self.leases.acquire(record.task_id, "execute", ttl=...)`

**Mechanism**: `LeaseManager.acquire_execution(task_id, *, ttl=None, worker_id="")`

**Behavior** (from lease.py detailed audit):
1. Read current execution lease for task
2. If ACTIVE, same operation="execute", not expired → same worker → renew heartbeat
3. If ACTIVE, same operation, not expired → different worker → raise `LeaseHeld`
4. If ACTIVE, expired → raise `LeaseExpired` (no silent mutation)
5. No active lease → acquire fresh execution lease

**Worker cannot usurp another's lease**. The execution lease identifies the owning worker and
controls whether that worker may continue executing. Expiry triggers recovery assessment.

### Worker Heartbeat (Renewal)

**Entry point**: `LeaseManager.renew_execution(lease, *, ttl=None)`

**Behavior**:
1. Only the owning worker may renew
2. Extends `last_heartbeat_at` and `expires_at`
3. Written to disk via `_write(lease)`

**Integration**: In `Aj._execute()`, the execution lease is renewed via heartbeat mechanism.
The TTL is set at acquisition (`timeout_seconds + 30`) and can be extended.

**Verified**: `test_crash_simulate_before_lease_release` tests the crash scenario where heartbeat
is not renewed (simulated crash). Recovery handles the expired lease.

### Worker Shutdown (Graceful)

**Mechanism**: `LeaseManager.release_execution(lease)`

**Behavior**:
1. Marks lease status = RELEASED
2. Writes `released_at` timestamp
3. Events "lease_released" recorded

**Integration**: Orchestrator `handle()` finally block:
```python
try:
    self.leases.release(lease)
except errors.AjError:
    pass
```

**Verified**: All 126 tests pass; lease released on normal exit path. Crash scenarios
(test_crash_safety.py) verify that absence of explicit release (crash) leads to lease expiry
and recovery, not data corruption.

### Worker Crash (Unexpected Termination)

**Scenario**: Worker process killed (SIGKILL, segfault, etc.) without releasing lease.

**Behavior**:
1. Lease remains ACTIVE on disk with `expires_at` in the future (or already expired if TTL elapsed)
2. Next operation on task: `LeaseExpired` or `LeaseHeld` raised (depending on lease type)
3. No data corruption: JSONL append-only writes are atomic (`_atomic_json` + `os.replace`)
4. Recovery: `Aj.recover()` or lease expiry assessment proceeds

**Test coverage**: 7 crash safety tests in `test_crash_safety.py` cover these scenarios.
Multiprocess contention test (`test_multiprocess_crash_contention`) covers 4-worker case.

**Verified**: No test leaves processes running or corrupts shared state. All processes terminate
cleanly or their effects are recovered.

### Worker-Generated Actions

Actions generated by workers (via `aj.echo` or internal actions) are recorded in:
- `record.actions_taken`
- `record.evidence`
- Journal events (EXECUTION_STARTED, EXECUTION_RESULT_RECORDED, EXECUTION_VERIFIED)
- Receipts (per-attempt durable receipts)

All are tracked for audit and recovery.

## Scheduler Overview

### Scheduler Implementation

**File**: `aj/scheduler.py`

**Public API**:
- `queue(task_id, *, priority=0, deadline=None)` — Add task to scheduler queue
- `run_once()` — Dispatch one eligible task from queue

**Current Integration**: The scheduler is **not deeply integrated** into the main
`Aj.handle()` pathway. Tasks are dispatched directly through the router. The scheduler
exists as a separate capability but is not used by default.

### Scheduler Functions (from code inspection)

```python
def queue(self, task_id, *, priority=0, deadline=None):
    """Add a task to the scheduler dispatch queue."""


def run_once(self):
    """Dispatch one eligible task from the scheduler queue."""
```

**Internal behavior** (from code inspection, not fully tested in suite):
- Reviews pending tasks
- Respects dependencies (`unsatisfied_dependencies()`)
- Respects lease state (avoids leased tasks)
- Respects priority and deadline
- Dispatches via `Aj.handle()` pathway or direct task claiming

**Gap**: The scheduler is not called from `Aj.handle()`. The main pathway uses the router
directly. Scheduler improvements would require orchestration changes.

### Scheduler vs. Router Dispatch

| Aspect | Scheduler (`aj/scheduler.py`) | Router (`aj/orchestrator.py:Router.route()`) |
|--------|------------------------------|---------------------------------------------|
| **Dispatch trigger** | `run_once()` call (external) | `Aj.handle()` entry point (every request) |
| **Dependency check** | `unsatisfied_dependencies()` | `unsatisfied_dependencies()` (same function in orchestrator) |
| **Lease check** | Avoids leased tasks | Same (lease acquired in handle() after authorization) |
| **Priority support** | `priority` parameter | `priority` parameter in `Aj.handle()` |
| **Deadline support** | `deadline` parameter | `deadline` parameter in `Aj.handle()` |
| **Default usage** | Not used by main pathway | Used by default (every `Aj.handle()` call) |

### Scheduler Assessment

#### Strengths

1. **Basic functionality present** — `queue()` and `run_once()` exist and have defined behavior.
2. **Same dependency/lease checks as orchestrator** — `unsatisfied_dependencies()` shared.
3. **Priority and deadline support** — Both scheduler and handle() support these parameters.
4. **Non-blocking** — Scheduler does not interfere with the main `handle()` pathway.

#### Weaknesses

1. **Not integrated into main pathway** — `Aj.handle()` does not call `scheduler.run_once()`.
   Tasks are dispatched via the router. Scheduler is "available but not used by default."

2. **No auto-scheduling** — No periodic scheduler process; no integration with `handle()` to
   make scheduler the default dispatch mechanism.

3. **Limited testing** — No test exercises the scheduler's `queue()`/`run_once()` pathway
   independently. Scheduler behavior inferred from code inspection only.

4. **No priority ordering guarantee** — `run_once()` documentation says "dispatch one eligible
   task" but does not guarantee priority ordering.

### Scheduler Integration Recommendation

If scheduler is to become the default dispatch mechanism, the following changes would be
required in `aj/orchestrator.py:Aj.handle()`:

1. After authorization, check scheduler queue before router dispatch
2. `run_once()` would need to return a task or None
3. If scheduler returns a task, use its existing state/lease; otherwise fall through to router
4. Scheduler and router would need shared lease state (currently both use `LeaseManager`)

**Alternatively**: Keep scheduler as a separate entry point (`python -m aj scheduler run`) for
operational use cases, while the main `Aj.handle()` pathway continues to dispatch via the router.

**Overall scheduler verdict**: **FUNCTIONAL BUT NOT INTEGRATED**. The scheduler exists and
has valid internal behavior, but it is not part of the main request dispatch pathway. This
is a design choice, not a bug. The router is the default dispatch mechanism.

- Worker heartbeat and crash recovery: 9/10 (7/7 crash safety tests pass)
- Worker graceful shutdown: 10/10 (finally block always attempts release)

### Recommendations

1. **If scheduler integration is desired**: Modify `Aj.handle()` to call `scheduler.run_once()`
   after authorization, falling through to router if scheduler returns None. This would
   make scheduler the default dispatch mechanism while maintaining backward compatibility.

2. **If scheduler remains separate**: Expose it as a CLI command (`aj scheduler run`) or
   operational API for advanced use cases. Document that the main `Aj.handle()` pathway
   uses the router, not the scheduler.

3. **Add scheduler tests**: At minimum, test `queue()` task addition and `run_once()` dispatch
   with dependency and lease checks. This would give independent coverage.

4. **Document the distinction**: Clarify in the code and documentation that the scheduler is
   an optional dispatch mechanism, not the default. The router is the default pathway.
