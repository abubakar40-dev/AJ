# 03 — Execution Readiness Matrix (Gate)

Scale: **READY** (evidenced for narrow scope) / **PARTIAL** (exists but gaps for mutating side effects) / **NOT READY** / **UNKNOWN** (external/Hermes-dependent).

| Gate | Question | Assessment | Evidence | Gap / condition |
|---|---|---|---|---|
| A. Execution boundary | Can AJ invoke narrowly defined external operation without arbitrary shell execution? | **READY (bounded, read-only only)** | Fixed argv list, `shell=False`, cli_path validation, deny-by-default capability/contract, controlled env, bounded timeout/output (`aj/hermes_adapter.py`, contract/tests) | Any future op must remain fixed-command/fixed-argv (or equivalently constrained interface) with explicit allowlist; no user-controlled args/shell |
| B. Capability isolation | Can a capability be independently registered/enabled/disabled/authorized/audited/tested/rejected without exposing unrelated ops? | **PARTIAL** | Runtime registers `hermes.status.read` only when attached+available (`runtime._build_execution`, `orchestrator.build`); contract/adapter deny non-allowlisted; AJ authorizer/capability registry/executable checks; audit/journal/receipts recorded per task path | Single-capability implementation today; multi-capability isolation (independent flags, per-capability argv/limits/contracts, independent enablement lifecycle) not yet generalized/tested |
| C. Permission model | Distinguish capability/operation/task/operator-trust context/authorization decision without pretending auth? | **PARTIAL** | Task IDs, correlation/operation/attempt IDs, capability_id, AJ allow decision, `local_trust` provenance explicit in v0 envelope/permission_context; Authorizer 5-level model exists; privileged reconciliation has separate identity-provenance model | `local_trust` is not human/remote authentication; no verified principal for external side effects; operation identity partly AJ-assigned (no Hermes-native external op ID for status probe) |
| D. Lifecycle | Represent submitted/accepted/running/completed/failed/rejected/timeout/unknown/manual review honestly? | **PARTIAL** | Contract status vocabulary + adapter mappings + task/journal/receipt states cover submitted→terminal and unknown/timeout/rejected cases; `operation_evidence` has intent/progress/terminal outcomes incl. incomplete-derived | Not all states semantically grounded in Hermes for current probe (no external running/cancel IDs); future mutating ops need truthful mapping to Hermes-native states where available, else unknown/manual review |
| E. Idempotency | Safe reasoning about duplicates? guarantees without native external key? | **PARTIAL** | AJ idempotency store/key claim+conflict detection in `orchestrator.handle`; operation/attempt/correlation IDs tracked | **No exactly-once.** Read-only status probe idempotent in effect but not a mutating commitment; without Hermes-native idempotency key AJ can only provide best-effort local dedupe/conflict detection and must treat ambiguous external outcomes as unknown/manual-review |
| F. Cancellation | Native cancellation vs local process termination vs request vs unknown? | **PARTIAL** | Local timeout causes process termination (best-effort kill/reap) mapped to timeout/terminated evidence; contract includes `cancel_requested/cancelled` states | `hermes gateway status` has no meaningful remote cancellable side effect; Hermes native cancellation for future ops **UNKNOWN** and op-specific. Must never equate local SIGTERM/SIGKILL with remote cancellation |
| G. Evidence | Explain requester/capability/authz/command-input/process outcome/external ID/observations without secrets? | **READY (process-level, read-only probe)** | v0 envelope + task evidence/audit/journal/receipts capture IDs, allowlisted capability/authz context, fixed argv template/sanitized resolved cli, bounded/redacted output, timings/status, `hermes_execution_id=null`; append-only evidence patterns exist | External operation/task identifiers **not provided** by status probe; for mutating ops must capture Hermes-returned IDs if any, else explicitly null/unknown; redaction best-effort; cross-store atomicity not guaranteed |
| H. Recovery | Behavior on persistence/process ambiguity/failure windows? | **PARTIAL** | Recovery manager/scans, leases/journal/receipts/operation evidence support incomplete/interrupted classification; honest unknown handling principles exist | Exact uncertainty boundaries for external side effects depend on Hermes interface (status/checkpoint/operation ID). If effect may have occurred but local outcome unknown, must be `unknown/requires_manual_review`, no auto-retry, no fabricated success |

**Overall gate for “first narrowly controlled mutating capability”: PARTIAL — design/controls partially ready, but mutating execution is NOT approved until a specific candidate passes its own contract/gap, side-effect, idempotency/cancellation, evidence, and security review and is implemented in a separate phase.**
