# 04 — Domain Model Decision Register (Stage 5A.1)

**Status:** Proposed decisions and open questions only. **No decisions here are approved architectural changes.**  
**Legend:** *Existing verified behavior* = evidenced in current source/tests/docs; *Proposed* = recommended for future; *Open question* = insufficient evidence; *Deferred* = intentionally later.

## A. Existing verified behavior (baseline, do not redesign implicitly)
| ID | Item | Evidence | Notes |
|---|---|---|---|
| EV-01 | `TaskRecord` is canonical persisted accountability unit with explicit state machine and append-only JSONL persistence/fail-closed semantics | `aj/task.py`, `tests/test_foundation.py`, `tests/test_task_persistence_fail_closed.py` | Terminal states never resurrected in normal flow; FAILED non-terminal. |

| EV-04 | Scheduler is basic deterministic leased dispatcher (`run_once`, optional ThreadPoolExecutor), not an orchestration engine | `aj/scheduler.py`, `tests/test_f2_scheduler_resume.py` | No admission/resource/backpressure/supervision. |
| EV-05 | Agent adapters are honest/logical boundaries; JARVIS/HELIX/Hermes not attached as working delegated execution runtimes in AJ | `aj/agents.py`, `aj/runtime.py`, `aj/hermes_adapter.py`, `aj --check` | Hermes status read-only capability exists but disabled/unattached. |

## B. Proposed decisions (future model)

| ID | Decision | Evidence | Alternatives considered | Reason for recommendation | Trade-offs | Required now or deferred | Confidence | Evidence that could change decision |
|---|---|---|---|---|---|---|---|---|
| PD-01 | Introduce first-class **`execution_id`** (durable AJ identity) for each managed execution/dispatch instance | Current model lacks execution entity; cannot unambiguously represent scenarios 2,8,9 in `02` | (a) Overload `attempt_id`; (b) overload lease_id; (c) keep implicit | Separates "managed execution slot" from "try" and from coordination lease; enables multi-execution-per-task and clearer cancellation/recovery scope | Added schema/complexity; migration/compatibility work later | **Required for 5A concurrency design correctness** (design now, implementation deferred) | **Medium-High** | Discovery that existing `attempts[]`+leases already provide sufficient unique, durable, unambiguous semantics in all audited call paths (unlikely per inspection) |
| PD-02 | Model **`attempt_id`** as first-class per-execution try with explicit lineage (retry => new attempt) | `attempts[]`/receipts/journal exist but conventional; retry/ambiguity cases need clarity (`02` scenarios 4,5,12) | (a) Mutable attempt record updated in place; (b) counter-only | Preserves immutable evidence per try, supports honest unknown/partial outcomes and replay analysis | More records/storage; need clear creation/ownership rules | **Required for design** (deferred impl.) | **High** | Evidence of strong existing invariants making current form sufficient without ambiguity (not observed) |
| PD-03 | Treat **Task** as stable logical/aggregate unit; allow 0..N executions/operations per task; do not equate task completion with single execution success unless evidenced | Current `TaskRecord` mixes intent and execution progress; concurrent delegation requires separation | (a) One task per execution always; (b) keep single-task-single-execution assumption | Matches user intent (submit logical work) while enabling fan-out/fan-in and independent execution tracking | Aggregation policy complexity (when is task complete/failed?) | **Required for design** | **High** | Product decision that AJ must remain strictly single-execution-per-task forever |
| PD-04 | Keep **Operation** as optional/minimal scoped intent entity (0..N/task) rather than mandatory for every simple task | Single `operation_id` on task is insufficient for concurrent multi-operation work, but adding mandatory operation layer everywhere is overhead | (a) Mandatory operation for all tasks; (b) no operation entity, only executions; (c) keep current single field | Balances expressiveness and simplicity; simple tasks can map 1:1 task-execution, complex tasks gain structure | Requires clear rules for when operation exists; potential ambiguity if omitted inconsistently | **Deferred (design option)**; define criteria before implementation | **Medium** | Evidence from 5A.2/5A.3 that scheduler/execution model needs operation as mandatory primitive |
| PD-05 | Represent **Agent** as stable logical capability/profile; record runtime **worker/instance holder** as transient evidence (not stable identity) | `aj/agents.py` provides logical adapters, not durable worker instances; leases already record `worker_id` (host:pid) | (a) Persist worker instances as primary agents; (b) ignore instance identity | Aligns with replaceable adapters and restart realities; avoids false stability of pids/processes | Must still capture enough holder evidence for debugging/recovery | **Required for design** | **High** | Need for durable agent-instance registry proven by implementation/runtime behavior |
| PD-06 | Use **typed dependencies** (task/op/execution) with explicit satisfaction/failure/unknown semantics; do not conflate dependency kinds | `depends_on` is task-level list with limited semantics (`02`) | (a) Task-only deps forever; (b) implicit ordering in scheduler only | Prevents incorrect unblocking/cancellation in fan-out/fan-in graphs; supports honest handling of `RECOVERY_REQUIRED/unknown` deps | More modeling and evaluation complexity | **Required for design**, implementation **deferred** | **Medium-High** | Evidence that all near-term workflows fit task-only deps with trivial semantics |
| PD-07 | Preserve **append-only evidence model** (journal/receipts/op-evidence/audit) extended with correlation to `execution_id/attempt_id`; no distributed DB/broker by default | Existing primitives strong and auditable; 8 GB host and project constraints | (a) Move to RDBMS/event bus/distributed log; (b) collapse stores into one mutable table | Fits modular monolith, restart/audit needs, and constraints; leverages existing code | Cross-store atomicity still absent; write amplification on unreliable storage | **Required (principle)** | **High** | Measured need for stronger transactional guarantees or throughput beyond local append-only design |
| PD-08 | **Never fabricate external/runtime IDs or outcomes**; represent unknown/ambiguous external effects explicitly (`unknown/requires_manual_review/lost`) | 4B.5/4B.6, recovery/consistency fail-closed behavior, AJ invariants | (a) Optimistic success; (b) auto-cancel assumptions | Safety/correctness over apparent completeness | More manual-review states and operator involvement | **Required now and ongoing** | **High** | Trusted, evidence-backed external contracts proving deterministic outcomes/cancellation semantics |
| PD-09 | Keep **AJ orchestration identity separate** from Hermes runtime identity and from JARVIS/HELIX internal state/memory | Project roles and 4B.x boundaries | (a) Embed Hermes session IDs as AJ primary keys; (b) share canonical DB across projects | Preserves boundaries, replaceability, and correctness of ownership | Requires correlation refs/mapping layer | **Required** | **High** | Explicit approved architecture change (none provided) |
| PD-10 | Concurrency safety must rely on **leases + idempotency + evidence reconciliation**, but still assume no global exactly-once | Existing lease/idempotency primitives; external effects uncertain | (a) Exactly-once claims; (b) no coordination primitives | Realistic on local/process-crash-prone environment | Cannot eliminate all duplicates/ambiguities | **Required** | **High** | New proven primitives or guarantees in runtime/adapters |
