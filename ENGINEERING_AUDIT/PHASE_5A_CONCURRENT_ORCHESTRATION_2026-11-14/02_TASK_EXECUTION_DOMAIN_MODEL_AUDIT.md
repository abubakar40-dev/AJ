## 3. Lifecycle state machines (actual, reconstructed)

### 3.1 Task states (actual)
**States:** `RECEIVED, UNDERSTANDING, PLANNED, WAITING_FOR_APPROVAL, AUTHORIZED, EXECUTING, VERIFYING, COMPLETED, FAILED, RECOVERING, RETRYING, ESCALATED, ABORTED, CANCELLED, RECOVERY_REQUIRED, CANCEL_REQUESTED, BLOCKED, DEAD_LETTER` (`aj/task.py`).

**Terminal:** `COMPLETED, ABORTED, CANCELLED, DEAD_LETTER` (property `TaskRecord.terminal`). **Non-terminal but failed/recovery states:** `FAILED, RECOVERING, RETRYING, ESCALATED, RECOVERY_REQUIRED, CANCEL_REQUESTED, BLOCKED` as modeled.

**Allowed transitions (`TRANSITIONS`):**
- `RECEIVED -> {UNDERSTANDING, FAILED, CANCELLED, ABORTED, RECOVERY_REQUIRED}`
- `UNDERSTANDING -> {PLANNED, FAILED, CANCELLED, ABORTED, RECOVERY_REQUIRED}`
- `PLANNED -> {AUTHORIZED, WAITING_FOR_APPROVAL, CANCELLED, ABORTED, FAILED, RECOVERY_REQUIRED, BLOCKED}`
- `WAITING_FOR_APPROVAL -> {AUTHORIZED, CANCELLED, ABORTED, FAILED, RECOVERY_REQUIRED}`
- `AUTHORIZED -> {EXECUTING, CANCELLED, ABORTED, RECOVERY_REQUIRED}`
- `EXECUTING -> {VERIFYING, FAILED, CANCELLED, ABORTED, RECOVERY_REQUIRED, CANCEL_REQUESTED}`
- `VERIFYING -> {COMPLETED, FAILED, CANCELLED, ABORTED, RECOVERY_REQUIRED}`
- `FAILED -> {RECOVERING, ABORTED, ESCALATED, DEAD_LETTER}`
- `RECOVERING -> {RETRYING, ESCALATED, ABORTED, DEAD_LETTER}`
- `RETRYING -> {EXECUTING, FAILED, ABORTED}`
- `ESCALATED -> {CANCELLED, ABORTED, COMPLETED, DEAD_LETTER}`
- `RECOVERY_REQUIRED -> {AUTHORIZED, FAILED, ABORTED, CANCELLED, DEAD_LETTER}`
- `CANCEL_REQUESTED -> {CANCELLED, COMPLETED, FAILED, ABORTED, DEAD_LETTER}`
- `BLOCKED -> {AUTHORIZED, PLANNED, CANCELLED, FAILED, DEAD_LETTER, RECOVERY_REQUIRED}`
- Terminals -> `()`.

**Rejection/guards:** `TaskRecord.transition` rejects illegal transitions (`AjError`/`CALLING_INVALID_STATE`) and rejects transitions from terminal unless `force=True`; terminal tasks not resurrected by normal flow. `TaskStore` update/save preserve lifecycle/identity/history fields for existing records (no silent status rewrite via generic update). Recovery paths converge/fail-closed per tests (`test_phase3c_recovery_integrity.py`, `test_phase3_lifecycle_reliability.py`).

### 3.2 Dependency-blocking behavior (actual)
- `depends_on` persisted on task; `Aj.handle` and `Aj.resume` check `unsatisfied_dependencies` and can transition/move task to `BLOCKED` with reason/audit/journal/memory notes (`aj/orchestrator.py`). `Scheduler.queue` reports waiting dependencies for `BLOCKED` tasks. **Full dependency satisfaction propagation/graph scheduling engine not observed.**

### 3.3 Retry/attempt behavior (actual)
- `TaskRecord.attempt`/`max_attempts` and `attempts[]` history exist; retry paths move through recovery/retrying/executing semantics (`FAILED->RECOVERING->RETRYING->EXECUTING` documented in `task.py` and exercised in tests), with bounded escalation (`test_orchestrator.py::test_retry_is_bounded_and_escalates_instead_of_looping`). Receipts/journal record attempt-linked outcomes. Idempotency prevents duplicate submission in-scope but does not imply external exactly-once. **Attempt/execution granularity not separated into distinct entities.**

### 3.4 Cancellation behavior (actual)
- `CANCEL_REQUESTED` and `CANCELLED` states exist; `EXECUTING -> CANCEL_REQUESTED` allowed; `CANCEL_REQUESTED -> {CANCELLED, COMPLETED, FAILED, ABORTED, DEAD_LETTER}`. `Aj.cancel/cancel_task` and store cancel semantics record cancellation (tests). **No evidence of remote/runtime cancellation semantics; local cancellation must not be equated to external side-effect cancellation.**

### 3.5 Recovery behavior (actual)
- `RECOVERY_REQUIRED` reachable from multiple states; recovery assessment in `Aj._assess_recovery`/`RecoveryManager.classify` yields decisions (replay/converged/blocked/terminal/manual-required) mapped conservatively; fail-closed on assessment errors. Completed/terminal tasks converge without resurrection; ambiguous completion evidence (receipt without terminal state) fails closed/no replay (`test_phase3c_recovery_integrity.py`). Active unexpired execution lease can block recovery; stale/expired handling is evidence/ownership dependent.

### 3.6 Execution/attempt/operation lifecycle (actual vs implicit)
- **Not a separate formal state machine** for `Execution` or `Attempt` entities. Evidence inferred from task states, `attempts[]` statuses, receipts (`execution_status`, verification), journal events, and lease lifecycle. This is insufficient to model multiple concurrent executions under one task.

## 4. Ownership and persistence boundaries

|---|---|---|---|---|---|---|

## 5. Current capability to represent concurrent scenarios (required assessment)

| # | Scenario | Classification | Evidence & reason |
|---|---|---|---|
| 1 | Two unrelated tasks executing simultaneously | **Representable with limitations** | Separate `TaskRecord`s/IDs, leases keyed per task, scheduler can run with `workers>1` via `ThreadPoolExecutor` (`aj/scheduler.py`). However no admission/resource isolation/orchestration supervisor, shared-process/thread contention, no proven correctness under real parallel dispatch beyond limited cases. |
| 2 | One task delegated to two independent sub-agents | **Not representable** (unambiguously) | No first-class execution/sub-agent instance entities, single task lifecycle/`operation_id` and no model for concurrent child executions under same parent task; agent adapters lack verified working delegation transport. |
| 3 | One sub-agent handling multiple tasks | **Representable with limitations** | Logical agent identity (`owner_agent`/adapter name) can be associated with different tasks; but no sub-agent worker instance tracking, capacity, or isolation model. |
| 4 | One task with multiple sequential attempts | **Representable with limitations** | `attempt` counter, `attempts[]`, receipts/journal per attempt, retry/recovery paths exist (`task.py`, `receipts.py`, tests). Semantics/structure of attempt records partially conventional. |
| 5 | One task with a failed attempt followed by a retry | **Representable with limitations** | `FAILED->RECOVERING->RETRYING->EXECUTING` and bounded retry/escalation evidenced (`test_orchestrator.py`, `test_phase3_lifecycle_reliability.py`). External side-effect safety remains capability/evidence dependent. |
| 6 | A parent task waiting for several child tasks | **Ambiguous / representable with limitations** | `parent_task_id/root_task_id` and child task creation exist; `depends_on` can reference tasks, `BLOCKED` state exists. No explicit parent-waits-for-children aggregation semantics or verified multi-child completion contract. |
| 7 | One child task failing while another completes | **Representable with limitations** | Independent child task records/lifecycles possible; parent aggregation/impact policy not explicitly modeled. |
| 8 | A task being cancelled while multiple executions are active | **Not representable** | Only single-task cancellation states (`CANCEL_REQUESTED/CANCELLED`) and no model of multiple concurrent executions per task; cannot scope/correlate cancellation to specific executions safely. |
| 9 | A process restart while several executions are running | **Ambiguous / representable with limitations** | Durable task/journal/receipts/leases/op-evidence support recovery assessment, but in-flight external/process state and multi-execution ownership may be unknowable; recovery is conservative/fail-closed in cases, not guaranteed complete. |
| 10 | Two AJ processes attempting to recover the same task | **Representable with limitations** | File/lease/task locking and operation/execution lease ownership checks provide coordination primitives (`aj/lease.py`, `aj/locking.py`), but cross-process recovery races/duplicate handling not comprehensively verified for all stores/paths. |
| 11 | One task depending on another task that enters `RECOVERY_REQUIRED` | **Representable with limitations** | Dependency IDs and blocking checks exist; `RECOVERY_REQUIRED` is a known task state, but dependency resolution policy on recovery/terminal outcomes is not a fully specified engine (behavior depends on `unsatisfied_dependencies`/resume logic). |
| 12 | An external runtime action whose final outcome becomes unknown | **Representable with limitations** (honesty required) | System has `RECOVERY_REQUIRED`, fail-closed recovery, receipts/journal/evidence gaps handling, and policy to avoid false success (`consistency`/recovery tests). But no dedicated `unknown` external-outcome execution entity/state contract across all paths; cannot claim cancellation or completion without evidence. |

## 6. Key audit findings (current model)
- **Strengths (verified/observed):** strong task accountability record, explicit state machine, append-only evidence primitives, lease separation (operation vs execution), fail-closed persistence/recovery tendencies, idempotency conflict handling, honest unattached external integrations.
- **Gaps/ambiguities for concurrent orchestration:** no first-class `Execution`/agent-instance entities; `operation_id` singular per task; attempts under-modeled for parallelism; dependencies task-level but not a verified concurrent DAG; scheduler lacks admission/resource/backpressure/supervision; cross-store atomicity absent; storage reliability risk on NTFS/WAL unresolved.
- **Non-goals preserved:** no Hermes lifecycle enablement, no fabricated external IDs, no exactly-once claims, `local_trust` not authentication.
